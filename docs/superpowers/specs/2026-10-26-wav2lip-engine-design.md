# Wav2Lip 数字人引擎（wav2lip）—— 设计文档

日期：2026-10-26
状态：已实现
取代：2026-10-25 的「轻量数字人引擎（lite / FeatherTalk）」

---

## 1. 背景

服务里原本有两个服务端驱动的数字人模型：GPU 专属的 MuseTalk 1.5，和纯 CPU 的
**FeatherTalk**（注册名 `lite`）。后者是 2026-10-25 那轮选型的产物，代价是
**个性化**：它的视觉 UNet 属于某个人，要用这个人自己的 3~5 分钟口播视频训练。
产品形态因此变成"上传一段这个人的口播视频"，而且每个形象都要单独训练一次。

Wav2Lip 是**通用**模型：一份权重驱动所有形象，不需要任何训练步骤。它的分辨率
低（96×96 的脸），画质不如 MuseTalk，但它是**唯一**一个既通用、又能实时、
又不需要按人微调的成熟开源模型。

本设计把 `lite`（FeatherTalk）整个换掉：注册名、代码目录、形象包格式、权重、
脚本、文档，全部换成 Wav2Lip。`lite` 这个模型名、它的形象行，以及它在磁盘上的
源码、权重与过程文件一并删除。

## 2. 选型

| 候选 | 结论 |
|---|---|
| **Wav2Lip**（Rudrabha，MIT） | **采用**。通用、免训练、36.3 M 参数、CPU 可实时。仓库在 `vendor/Wav2Lip`，锁 commit `bac9a81`。 |
| FeatherTalk（anliyuan，Apache-2.0） | **出局**。要按人训练：制作流程变成"上传 3~5 分钟素材 + 训练专属 UNet"，每个形象一次训练，且权重只对一个人有效。 |
| Ultralight-Digital-Human | FeatherTalk 的前身，音频前端是 HuBERT-Large（1.2 GB，比 FeatherHuBERT 慢约 40 倍）。 |
| LiteAvatar（达摩院，MIT） | 权重在 ModelScope，但三段式流水线的前端是中文 ASR（Paraformer-large ~1 GB），形象来自预置画廊而非任意照片。 |
| CASync | 19.8 M / 4.08 GFLOPs，指标漂亮，但仓库只有 3 star、需按身份微调、无官方 ONNX。 |
| SadTalker / LatentSync / Hallo / EchoMimic / EMO | 全 GPU，显存 6–24 GB。出局。 |

Wav2Lip 的代价是**分辨率**：它只重绘一张 96×96 的脸框，而 MuseTalk 重绘的是
下半脸的高分辨率融合。这是"通用免训练"与"照片级唇形"之间的取舍。

## 3. 架构

```
制作端（后台任务）                      服务端（每 100 ms 音频块）
──────────────                        ──────────────────────
上传口播视频（或一张照片）
  │
  ├─ 解码 → 720×1280 画布帧
  ├─ S3FD → 每帧人脸框（+10px 下边距 + 5 帧平滑）
  ├─ 静音 mel 窗口重绘同一批帧  ──►  wav2lip/idle_frames/*.jpg
  └─ 产出形象包：
       wav2lip/frames/*.jpg    运动源帧（头/身体）
       wav2lip/coords.json     每帧人脸框
       wav2lip/meta.json
                                     │
                                     ▼
                        mel 频谱（滚动）→ 16 帧窗口
                        Wav2Lip 生成器 → 96×96 脸
                        贴回人脸框 → 720×1280 RGB
```

一个模型 = 一条流水线 + 一个引擎（`dh-server/dh_server/model_registry.py`），本设计注册
`wav2lip` 模型，流水线与引擎成对注册。形象包里**没有专属权重**——这是与
FeatherTalk 最大的结构差异。

## 4. 关键决策

### 4.1 通用模型：形象包里没有权重

FeatherTalk 的形象包带一份 `visual.pth`（这个人专属的视觉 UNet），所以"加载
形象"要加载 22 MB 权重、"换个人"要重新训练。Wav2Lip 的权重是全局的，形象包里
只有**帧 + 人脸框**，于是：

- 形象制作不需要训练，后台任务只做检测与重绘；
- 加新形象不需要新权重，磁盘占用从「每人 22 MB」降到「每人几百 KB 的 JPEG」；
- 引擎只持有一份权重，缓存里放的是每个形象的帧。

代价是形象包的帧必须是**有人说话**的素材（见 §4.4）。

### 4.2 mel 窗口的未来部分填静音（口型同步）

上游 Wav2Lip 的 mel 窗口是 **16 帧 = 200 ms**，且从当前帧自己的音频开始向后取：

```
mel[int(80 * i / fps) : int(80 * i / fps) + 16]
```

也就是说，渲染第 i 帧时，模型看到的是「第 i 帧的音频 + 之后 160 ms 的音频」。
离线推理时这不是问题（整段音频都在），但实时流里**未来的音频还没到**。

有两条路：

| | 画面延迟 | 窗口内容 |
|---|---|---|
| 等未来音频到齐再渲染 | 200 ms（画面比声音晚） | 与训练完全一致 |
| 未来部分填静音 | 0 | 当前音频是真的，后面是静音 |

本设计选**填静音**。理由是本服务把「画面永不落后于声音」当作硬约束（浏览器以
音频轨做 A/V 时钟基准，200 ms 的偏移肉眼可见），而静音正是上游在音频结尾用的
填法（`power_to_db` 之后的归一化把静音压到 -4）。

代价是模型看到的是一个「说完就断」的窗口，而不是完整的 200 ms。实测：用零填充
的窗口渲染出来的脸，与用完整窗口渲染出来的脸，逐像素平均差 **0.5%**（最大
0.35/1.0），嘴形一致——因为音频编码器把整个 200 ms 压成一个时间步，而口型由
窗口开头那 40 ms 决定。

### 4.3 裁剪几何：S3FD + 上游的 padding 与平滑

上游的裁剪几何是围绕 **S3FD** 定义的：网络就是在 S3FD 找到的脸上训出来的，
所以检测器是模型的一部分，不是可以替换的配件。本服务直接用 vendored 的
`face_detection`，并复刻上游的两处调整：

- **下边距 +10 px**：裁剪框必须含下巴，否则模型没有嘴可画；
- **5 帧滑动平均**：检测器抖一像素，贴回去的脸就会游。

这两步都是纯函数，可以在没有 torch 的环境下断言。

### 4.4 闭嘴空闲轨

形象包的帧来自一段**人物在说话**的视频（模型就是拿这类素材练出来的），直接回放
会让角色在会话没说话时也在演说话。所以构建时用**静音 mel 窗口**把同一批帧重绘
一遍，作为 `wav2lip/idle_frames/`：动作不变、嘴闭着。运行时只是多解一个 JPEG，
不占算力。

这与 MuseTalk 的空闲轨（直接回放源视频）不同，原因见 §4.1：MuseTalk 的形象包
里没有"必须来自说话视频"这个约束。

### 4.5 设备：有 GPU 用 GPU，没有就用 CPU

Wav2Lip 足够小，**纯 CPU 也能实时**；但这台机器有 GPU 时，带宽与延迟都宽裕
得多。于是设备是**探测出来的**，不是配置出来的：模型和检测器都跑在
`pick_device()` 选出的设备上，画面本身（解码、裁剪、贴回）始终在 CPU。

| | 每个 100 ms 音频块（2~3 帧） |
|---|---|
| GPU（RTX 50 系） | **21 ms** |
| 纯 CPU | **79 ms** |

CPU 路径仍然满足 25 fps（预算是 100 ms），GPU 路径有 4 倍余量。

### 4.6 vendored 代码的导入方式

上游仓库是一棵**扁平的树**（根目录下有 `models/`、`face_detection/`、`audio.py`、
`hparams.py`）。把它加进 `sys.path` 会把 `models` 和 `audio` 这两个名字发布给
整个进程。所以本服务把它挂成一个**私有包**（`_wav2lip_vendor`），只有明确
import 的模块可达（`dh-server/dh_server/wav2lip/vendor.py`）。

### 4.7 cuDNN benchmark 的全局副作用（一个真实的坑）

vendored 的 S3FD 检测器在自己跑的时候会把 `torch.backends.cudnn.benchmark` 打开，
而且是**全局**打开的。开着它，**每一个新的输入形状**都要做一次穷举的算法搜索
——本服务实测每个新形状 **13.5 秒**。表现是：刚构建完形象的第一次会话，前两个
音频块各卡 13 秒。

修法是检测器跑完就把这个开关还原（`dh-server/dh_server/wav2lip/faces.py`）。检测器自己的
形状是固定的，它需要这个开关的场合只有它自己那一次调用。

同一个坑对 MuseTalk 也成立：Wav2Lip 的构建任务跑过之后，MuseTalk 的每个新
形状也会各付 13 秒。所以还原发生在检测器里，而不是模型里。

### 4.8 权重的获取路径

`huggingface.co` 与 Google Drive 在本网络不可达，所以权重走 **hf-mirror** 代理：

| 文件 | 大小 | sha256 |
|---|---|---|
| `wav2lip_gan.pth` | 435 801 865 | `ca9ab7b7…d7ac3d8` |
| `s3fd.pth` | 89 843 225 | `619a3168…d59b33543` |

`scripts/fetch_wav2lip_weights.sh` 按 sha256 校验；`s3fd.pth` 在 hf-mirror 与
检测器自己的站点（`adrianbulat.com`）上字节一致。

## 5. 实测

硬件：Windows 11 / RTX 50 系 / `.venv-musetalk`（torch 2.11 + cu128）。

| | 数值 |
|---|---|
| 形象制作（10 s 视频 / 251 帧） | **56 s**（几乎全是逐帧 S3FD 检测） |
| 引擎加载（权重 + 一次预热前向） | **2.1 s** |
| 首个音频块 | **40 ms** |
| 稳态音频块（GPU） | **21 ms** / 100 ms |
| 稳态音频块（纯 CPU） | **79 ms** / 100 ms |

## 6. 不做什么

- **不训练、不微调**：Wav2Lip 是通用模型，服务不提供任何训练入口。
- **不做超分**：96×96 的脸框直接贴回 720×1280 的画面，不做放大增强。
- **不做多身份/多人脸**：一帧里检测到多张脸时取第一张。
- **不改上游的裁剪与贴回**：整个脸框被预测结果替换，与上游 `inference.py` 一致。
